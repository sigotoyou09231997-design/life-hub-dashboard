## これは何か

`docs/requests/` に置かれた依頼（Cowork が書いた Markdown）を確認し、着手できるものを実装して、
型チェックとテストが通れば本番（`main`）へ反映するための手順。ワークスペース（`~/Desktop/WEBアプリ用`）の常駐から
`claude -p "/cowork-check" --permission-mode acceptEdits` としてヘッドレス起動される想定。
このアプリ専用のスクリプトは持たず、`../scripts/` にあるワークスペース共通のものを使う。

このプロジェクトの本番反映ルールは `CLAUDE.md` に書かれている。矛盾する場合は `CLAUDE.md` が優先。

## 手順

### 1. 状況を確認する

```
bash ../scripts/cowork-watch.sh --app "todoアプリ"
```

出力の「依頼ステータス」表で、依頼ごとに次のいずれかが分かる。

- `着手可（新規）` / `着手可（更新）` … 今回処理する
- `実装済み` … 何もしない
- `保留中` … `.cowork/waiting.txt` に理由が書かれている。**触らない**。前回すでに保留にした理由が
  解消されていない限り、同じ提案を繰り返さない

`.cowork/waiting.txt` の中身も必ず読むこと。

### 2. 依頼ごとに、着手できるか判断する

依頼ファイル本体を読み、「何を変えたいか／どの画面・どのデータか／既存データの扱い」を把握する。

次のいずれかに当てはまる依頼は、**実装せず** `.cowork/waiting.txt` に依頼ファイル名と理由を追記して
止める（既存の内容は消さず追記する）。

- 何をしたいのかが依頼から読み取れない
- Supabase のスキーマ変更（`supabase/sql/` 配下の変更）が必要 — SQL は人が本番で実行する必要がある
- 本番データを消す／作り直す性質の変更
- Dexie の主キー変更など、`src/db/schema.ts` のバージョンチェーンを壊しうる移行

文言・色・並び順・細かい UI の詰めなど、依頼に書かれていない細部は自分で妥当な案を採って進めてよい。
何を自分の判断で決めたかは、最後の報告で明示する。

### 3. 実装する

- 既存のコード規約・パターンに合わせる
- 依頼された範囲を超える変更を勝手に追加しない
- 1つの依頼につき、意味のある単位でコミットする（複数依頼をまとめて1コミットにしない）

### 4. 検証する（省略・無効化しない）

```
npx tsc --noEmit
npm test
```

**両方とも通った場合のみ**次に進む。1つでも落ちたら、直せるならその場で直して再実行する。
直せない場合はコミットせず、その依頼は `着手可` のまま残す（＝実装しない）。
テストを飛ばす・無効にする・削除して通すことで条件を満たしたことにはしない。

### 5. コミットして反映する

現在のブランチ（作業ブランチ）にコミットし、push する。

```
git add <変更したファイル>
git commit -m "<内容が分かるメッセージ>"
git push
```

その依頼について型チェック・テストが通り、コミットも完了したら、`.cowork/state.tsv` に
「実装済み」として記録する。

```
bash ../scripts/cowork-watch.sh --app "todoアプリ" --update
```

**注意**: `--update` は実装・テスト通過・コミットがすべて終わってから実行する。途中で止めた依頼や
保留にした依頼については実行しない（実行すると次回そのままにされ、差分が消えてしまう）。

処理できた依頼がある場合は、`CLAUDE.md` の本番反映ルールに従って `main` へマージし push する
（型チェック・テストが通った変更のみ。強制プッシュ・履歴の書き換えはしない）。

### 6. 報告する

このスキルの実行結果として、以下を簡潔にまとめる。

- 実装して本番に入れた依頼（何をしたか）
- 実装にあたって自分の判断で決めた細部（文言・色・並び順など）
- 保留にした依頼とその理由（`.cowork/waiting.txt` に書いた内容）
- 何も対象がなかった場合はその旨
